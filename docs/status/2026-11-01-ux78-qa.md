## Annex

### A. The 23 pre-existing visual failures

All are phone-portrait. Single root cause: **the layout viewport blows out** — the page renders wider than the device, so mobile zooms out to fit, and the resulting layout width then trips `HERO_NAME_MIN_WIDTH = 381`.

Rendered width vs device width per failing row:

| Row | Device | Rendered | Factor | Extra failures |
|---|---|---|---|---|
| 360x640 | 360x640 | 647x1151 | 1.80× | hero name hidden |
| 390x844 | 390x844 | 631x1366 | 1.62× | hero name truncated |
| 414x896 | 414x896 | 631x1366 | 1.52× | hero name truncated |
| 360x780 | 360x780 | 647x1402 | 1.80× | hero name hidden |
| 360x640@130 | 360x640 | 721x1282 | 2.00× | **spill=5px > 2px**; **rules text cut** (Hammerfall, Anvil Blow); hero name hidden |
| 360x780@130 | 360x780 | 721x1563 | 2.00× | hero name hidden |
| 390x844@130 | 390x844 | 705x1526 | 1.81× | hero name truncated |
| 412x915@130 | 412x915 | 705x1566 | 1.71× | hero name truncated |
| the same 8 sizes × `+hand10` | — | — | — | as above |
| the same 8 sizes × `+hand7` | — | — | — | as above |

Reason-class counts across the 23 rows: 23 × `page wider than the screen`, 23 × `HUD hero name` (11 hidden / 12 truncated), 3 × `stageSpillPx` (5px on `360x640@130`, 4px on `360x640@130+hand10`, 4px on `360x640@130+hand7`), 3 × `rules text hidden`.

**Correction to the brief's phrasing:** the brief described real content clipping on "the two 360x640@130 rows". The matrix has **three** `360x640@130` rows (plain, `+hand10`, `+hand7`) and **all three** carry positive spill: 5px, 4px, 4px, each with cut rules text on the plain and `+hand10`/`+hand7` variants. This is a wording count, not a regression: the baseline log carries exactly the same three values.

**Artifact reproduction:** the same matrix run against the committed `release/` artifact (HEAD content, commit `a8f9709`) produced identical numbers — `647x1151` at 360 wide, `631x1366` at 390/414, `721x…` at 130% scale. Corroborated independently by the I18N-1 ledger entry in `docs/status/STS-PARITY-ROADMAP.md`, which already records "the 390x844 HUD overflow is PRE-EXISTING".

**Not a defect in these slices, but an open product decision:** whether phone-portrait ships with a HUD that overflows is the owner's call, not QA's. It is pre-existing and unchanged by UX-7/UX-8.

### D. Plumbing notes for future runs

- `viewport-check.mjs --port N` is the **Chromium DevTools** port and also names the profile (`/tmp/dlb-viewport-N`). It is not the app server port. Passing `--port 9410` alone leaves the app pointed at the default `5173` and the run fails on connection, not on layout.
- The app URL comes from `--base 'http://host:PORT/src/web/index.html?seed={seed}'`. The `{seed}` placeholder is required; a positional BASE still works but cannot do the seed sweep.
- `npm test` output carries **no filenames** — only titles. Proving a new test file was included therefore means matching its titles into the suite log (here: all 11 `status-fold.test.js` titles found).
- Headless Chromium is not always reaped when the checker is killed. If a run was SIGTERM'd, check `ps` for a chromium carrying the run's profile signature (`/tmp/dlb-viewport-<port>`) before starting the next one. This pass found none.
- `shots/viewport/` holds 255 PNGs after the run and is gitignored (`.gitignore:9: shots/`).
